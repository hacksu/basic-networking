Slide 505:00-06:00

Why do OSI and TCP/IP exist?

  • Begin with the problem: devices from different vendors and networks need shared rules. Layering divides the work so an application can use multiple link technologies through consistent interfaces.
  • OSI is a reference model for coordinating and describing communication responsibilities. TCP/IP is the deployed Internet protocol suite, with concrete formats and behavior. A four-layer TCP/IP model describes that suite; it is not a second packet sent beside the first.
  • Use two practical benefits: engineers can isolate a fault to a layer, and a Wi-Fi/Ethernet change need not rewrite the application protocol. Here OSI refers to the reference model; this talk does not cover the historical OSI protocol suite. Sources: ITU-T X.200 and RFC 1122.
Slide 606:00-08:00

OSI: where would you look?

  • Start at the bottom with a cable, then move upward. Do not ask the audience to memorize all seven names.
  • Contrast an unplugged cable, a missing route, and an HTTP error. Similar symptoms at the browser can have different causes.
  • Use one failure at a time: no link light suggests checking cable and port state; an incorrect prefix or route is a network-layer concern; a reachable TCP service returning an HTTP error points upward. Symptoms can overlap, so this is a map for investigation rather than proof from a single signal.
Slide 708:00-09:00

Data, segments, packets, and frames

  • PDU means protocol data unit. The same application bytes can appear inside a transport unit, an IP packet, and an Ethernet frame; the names identify which layer is being discussed.
  • TCP carries a byte stream, so one application message may span multiple segments or share a segment with other data. UDP preserves datagram boundaries. IP can also carry other protocols, such as ICMP, rather than always TCP or UDP.
  • The OSI labels are a way to describe responsibilities. They do not require seven separate headers in the Ethernet/IP/TCP example, and there is no extra OSI wrapper to find in Packet Tracer. At reception the host interprets headers to deliver the payload upward.
Slide 809:00-10:00

TCP/IP uses fewer layers

  • This is the four-layer teaching model. Some materials split the link layer into physical and data link.
  • The mapping is approximate. Keep attention on what each layer does.
  • A DNS message using UDP still belongs to the TCP/IP suite. Ask attendees to place Ethernet, IPv4, TCP, and HTTP into the four-layer model. Keep the mapping brief so the worked delivery examples have time.
Slide 910:00-11:00

Encapsulation: each layer adds context

  • Read top to bottom: the first row shows an Ethernet header, IP payload, and FCS trailer. The next row expands the IP payload into an IP header and TCP segment. The last row expands TCP into its header and application bytes.
  • Each header serves its own scope: Ethernet MAC addresses deliver on the local link; IP addresses identify network-layer endpoints; transport ports identify endpoints within hosts. The receiver interprets these layers in reverse.
  • FCS is frame check sequence, used to detect frame errors. Ethernet does not retransmit a frame because its FCS failed; recovery, if needed, belongs to an upper protocol or application. This schematic is not to scale and omits physical preamble and other framing details.
Slide 1011:00-13:00

Which header answers which question?

  • Use a packet inspection mindset. Ethernet source/destination MACs identify the link endpoints, and EtherType identifies the carried protocol. IPv4 source/destination IPs and TTL support network delivery; Protocol selects the upper-layer interpretation.
  • TCP ports identify connection endpoints. Sequence and acknowledgment numbers describe progress in its byte stream, while flags include SYN, ACK, FIN, and RST. UDP supplies source/destination ports, length, and checksum but no built-in sequence or acknowledgment fields.
  • TTL is decremented at routers to limit a packet lifetime and stop indefinite circulation. IPv6 uses Hop Limit and Next Header. These are selected fields, not a byte-accurate diagram of every field. Sources: RFC 791, RFC 8200, RFC 9293, and RFC 768.
Slide 1113:00-14:00

Three different addresses

  • A MAC address can be assigned or randomized. It is not permanent identity or strong authentication.
  • A host can have multiple interfaces and IP addresses. TCP and UDP have separate port spaces.
  • Ethernet MAC addresses commonly use six octets, written as hexadecimal pairs. Compare that local forwarding identifier with a routable IP destination and a TCP/UDP port identifying a transport endpoint. All examples are illustrative; a MAC can be reassigned or randomized.
Slide 1214:00-15:30

How does a switch learn?

  • Use an initially unknown B as the example. A sends through port 1, so the switch learns A’s source MAC in that VLAN. It looks up B’s destination MAC separately. If B is unknown, it floods to eligible other ports rather than somehow knowing the right wire.
  • B’s reply arrives through port 2, teaching B’s location. A is now known, so the reply can be forwarded toward A. Learning entries age, and a source moving ports can update the learned path.
  • A hub repeats signals without building this forwarding table. The unmanaged TP-Link still performs MAC learning. These example port numbers are conceptual, not a claim about the exact Catalyst interface names.
Slide 1315:30-17:00

What does /24 actually mean?

  • IPv4 has 32 bits. A /24 reserves 24 bits for the prefix and leaves eight for the host portion; the dotted mask is 255.255.255.0. Compare each destination with A’s prefix: .50.20 is local, while .51.20 needs a route beyond that subnet.
  • For this ordinary /24, .0 names the subnet and .255 is the directed broadcast address. Do not assign those to the two lab hosts. Other prefix lengths behave differently, so matching three decimal octets is only a shortcut for this example.
  • Ask whether changing the switch alone would make .50.10/24 and .51.20/24 one subnet. It would not; addressing and routing still matter.
Slide 1417:00-18:30

ARP: from an IPv4 address to a MAC

  • A knows B’s IPv4 address but needs an Ethernet destination. With no cached mapping, A broadcasts an ARP request; B normally replies directly with its MAC. A can then transmit an IP packet in a frame addressed to B.
  • Point out two independent tables: the host’s ARP cache maps an on-link IPv4 address to a MAC, while the switch maps source MACs to VLAN ports. The switch learns from incoming frames, including ARP traffic.
  • ARP remains on the local link. For a remote IP destination, A resolves the gateway’s MAC instead of broadcasting a question across the internet. Repeated pings may reuse cached entries, which explains why the demo will not show an ARP request every time.
Slide 1518:30-20:00

Remote IP, local next hop

  • The gateway address here is illustrative. The offline demo deliberately has no gateway. First choose a route; when that route uses this gateway, ARP resolves the gateway’s local MAC.
  • The first frame targets the gateway MAC while the enclosed IP packet targets 192.168.51.20. The router examines the IP destination, chooses its outgoing route, decrements TTL, and constructs new link-layer framing.
  • For ordinary routing, distinguish the continuing IP destination from link addresses that change by hop. NAT is a separate rewriting operation often combined with routing in home and travel routers. The gateway still needs a usable onward route; its existence does not guarantee delivery.
Slide 1620:00-23:00

IPv6: the same job, more space

  • The 2001:db8:: example is reserved for documentation. Show hexadecimal groups and compressed zeros briefly.
  • IPv6 link-local addresses use fe80::/10. Neighbor Discovery uses ICMPv6 for functions including neighbor and router discovery.
  • IPv6 is not automatic encryption. Do not promise that the travel router or any upstream supports global IPv6.
  • Expand 2001:db8::10 to 2001:db8:0:0:0:0:0:10. Double colon compresses a run of zero groups and may appear only once in an address. The larger space changes notation and address management, not the need for local delivery and routes.
  • Contrast Neighbor Discovery using ICMPv6 with IPv4 ARP. Link-local addresses support local communication but do not establish global reachability. Keep subnet arithmetic and the full IPv6 configuration process for follow-up questions.
Slide 1723:00-24:00

TCP and UDP

  • TCP delivers an ordered byte stream, not application messages. One socket write can be split across multiple reads, or multiple writes can be combined. Applications often add length prefixes, delimiters, or a protocol parser.
  • UDP preserves individual datagrams but does not supply automatic retransmission or ordering. The application decides whether and how to recover from loss. Neither transport inherently encrypts data, and neither makes every application faster.
  • For TCP, missing bytes can delay delivery of later bytes in the same stream while recovery occurs. That is useful for completeness but a tradeoff when freshness matters. Introduce the next slide as a requirements choice, not a vendor or performance ranking.
Slide 1824:00-25:00

When does TCP or UDP make sense?

  • Choose based on the application requirements. TCP is useful when a reliable ordered stream is the desired interface, such as SSH or many database/file-transfer protocols. The application still needs its own message boundaries and error handling.
  • For interactive voice or game-state updates, a late update may be less useful than a newer one. UDP lets the application or higher protocol decide which data to retry, discard, or reorder. UDP itself does not promise low latency, and applications still need congestion control and a loss strategy.
  • These are examples, not universal rules. Classic DNS supports UDP and TCP. HTTP/3 uses QUIC over UDP, and QUIC supplies reliability and other transport behavior above UDP. A reliable UDP-based protocol is not a contradiction. Sources: RFC 8085, RFC 1035, and RFC 9114.
Slide 1925:00-26:00

TCP: establish, acknowledge, recover

  • Walk the SYN, SYN+ACK, ACK exchange in order. Both sides synchronize sequence-number state before the usual application-data exchange. The diagram omits optional extensions and simultaneous open.
  • Sequence numbers track bytes. Acknowledgments report progress, and loss can trigger retransmission. Flow control protects receiver capacity; congestion control responds to network capacity. Neither makes a failed connection impossible.
  • IP addresses plus ports distinguish connections. TCP does not supply encryption or application success; HTTPS adds TLS, while HTTP/3 uses QUIC over UDP.
Slide 2026:00-27:30

DHCP: how a host gets its settings

  • Discover, Offer, Request, ACK is the common initial DHCPv4 exchange. A client starting without a lease can broadcast to find a server. The server supplies a lease and configuration options.
  • Leases expire and can be renewed; renewal does not always repeat all four initial messages. The router advertised by DHCP and the DNS resolver are different settings, even when one physical box performs both roles.
  • Connect this to the demo: the isolated Ethernet hosts use static settings, while the GL.iNet can supply automatic settings. A successful lease proves neither internet reachability nor working DNS. IPv6 uses different configuration mechanisms.
Slide 2127:30-30:00

DNS: a name is not a route

  • An application asks for a name. A local cache or configured recursive resolver can supply an answer; on a cache miss, a recursive resolver can consult other DNS servers. A and AAAA records provide IPv4 and IPv6 addresses.
  • DNS records can be reused while cached according to their TTL. A hostname can have multiple addresses. DNS does not choose the host’s Ethernet next hop or establish an application connection.
  • Walk the full story: obtain settings, resolve the name, choose a route, resolve the local next hop, then attempt the transport and application exchange. Those stages can fail independently. DNS is not limited to UDP, and an address response alone does not prove a website works.
Slide 2230:00-32:00

DSL and cable

  • Do not attach universal speed numbers to these technologies. Actual service depends on equipment, deployment, plan, and conditions.
  • The modem handles access signaling; routing is a separate function even when one box combines both.
  • The access medium is only one part of the path. Explain the distinction between a modem terminating access signaling and a router forwarding IP, even when the functions share a box. Neither technology replaces Ethernet/Wi-Fi inside the local network.
Slide 2332:00-35:00

Fiber and cellular

  • Fiber is not always dedicated or symmetric. Cellular is not the same link as Wi-Fi. The hotspot path on this slide is a conceptual example; the GL.iNet travel router is not assumed to contain a cellular modem.
  • Compare medium, mobility, deployment constraints, latency, and upload needs verbally. Avoid ranking technologies from one speed test.
  • Compare capacity with latency: bits per second describe rate, while latency describes delay. A high advertised rate does not promise low delay or high upload throughput. Fiber sharing and cellular radio conditions still matter; do not attach universal rankings or benchmark numbers.
Slide 2435:00-36:00

The whole path sets the limit

Check show interfaces status for the actual negotiated speed and duplex. The four SFP slots remain unused without modules.
  • Other traffic, protocol overhead, host performance, and radio conditions can reduce throughput further.
